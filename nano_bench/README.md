# Nano bench 0.4.0 — автономный ADC, ДПКВ по умолчанию и протокол wire 1

Изолированный модуль для Arduino Nano ATmega328P. После одного `ADC_STREAM_START` Nano сама измеряет A6/A7 и отправляет каждый результат отдельным UART-событием; ПК только принимает данные, не опрашивает каждый отсчёт. С 0.4.0 после каждого reset (включая открытие COM) генератор ДПКВ стартует автоматически: шаблон 48-1, инверсия включена (D8 — raw, D9 — инверсный), 1000 rpm. Это рабочая разработка стенда, **не подтверждённый стенд ЭБУ**. Новый модуль не поддерживает старый Ardu-Stim GUI: старые `ardustim`/UI остаются legacy и не заменяются.

## Быстрый запуск

Требуется Python и зависимость `pyserial` из [`requirements.txt`](requirements.txt). Пример для Windows:

Из корня репозитория Ardu-Stim:

```powershell
cd nano_bench
python -m pip install -r requirements.txt
python host\bench_cli.py --port COM79 nano-stream --period-us 10000 --channels 6 7 --seconds 10
```

Это 100 Гц **на канал**: каналы измеряются последовательно, не одновременно. Остановить можно также после числа сообщений: `--count N`. Команда выполняет один START, читает события, затем в `finally` посылает STOP. Для одного канала используйте `--channels 6` или `--channels 7`.

Пример API, также с одним START и без `ADC_READ` для получения отсчётов:

```python
from host.bench_client import BenchClient

with BenchClient("COM79") as stand:
    stand.nano_adc_stream_start(period_us=10_000, channels=(6, 7))
    try:
        for sample in stand.iter_events(duration=10):
            print(sample.id, sample.channel, sample.value, sample.timestamp_us)
    finally:
        stand.nano_adc_stream_stop()
```

`iter_events` выдаёт и ADS1115-события, если ADS-поток включён; различайте устройства по `sample.id` (5 — Nano, 2 — ADS1115). CLI выводит JSONL с host-monotonic меткой. `--no-reset` — best effort, не предотвращает аппаратный автосброс на проверенном CH340; для гарантии удержания состояния через открытие порта требуется аппаратно отключить автосброс. Держите одно соединение на последовательность команд. Помните: каждый сброс заново включает генератор ДПКВ (48-1/1000 rpm).

## Кратко о возможностях и ограничениях

- UART по умолчанию 1 000 000 бод, 8N1; отдельная резервная сборка — 500 000. 921 600 не поддерживается: на 16 MHz фактический baud около 1 MHz, ошибка +8.507% относительно 921600.
- Native ADC: A6/A7, код 0..1023, опора AVCC. По умолчанию оба канала, период 10 000 мкс на канал (100 Гц). Допустимый период 1 000..10 000 000 мкс. Каждый результат — отдельное событие; после START ПК не посылает запросы на каждый отсчёт.
- ADS1115: I2C по умолчанию 0x48, ALERT/RDY на D3, I2C 400 kHz. TPL0501: SPI до 8 MHz. Возможность управления устройствами не означает, что их физическая работа или выходное значение проверены.
- ДПКВ (0.4.0): boot default — pattern 3 (48-1), invert=1, 1000 rpm; после reset генератор запущен сразу. Смена — `stop`, затем `crank-config` и `rpm`; D8 — raw, D9 — инверсный. Формула пропуска та же, что у остальных справочных шаблонов.
- Исторический аппаратный прогон прошивки 0.3.0: 4004 native-отсчёта за ~20 с на двух каналах; параллельно 2002 native + 8898 ADS за ~10 с; 6004 native-отсчёта за ~3 с при 1000 Гц/канал. В указанных прогонах ошибок и потерь не зарегистрировано. Это измерения MCU/протокола, не гарантия жёсткого джиттера или точности напряжения.
- Текущая сборка 0.4.0: 13 378 байт Flash, 1 152 байта static RAM (историческая 0.3.0: 13 432/1 152); 896 байт остатка по отчёту линкера — не измерение stack high-watermark. Исторические офлайн-тесты: 26; scheduler-тесты моделируют планировщик, а не выполняют код на AVR.
- ЭБУ, CAN, K-line и J2534 не использовались. В проверке 0.3.0 ДПКВ не запускался; в 0.4.0 генератор запущен и проверен на уровне команд/статуса (автостарт, echo, BAD_ARGUMENT), форма сигнала осциллографом не измерялась. На A6/A7 не подавалось контролируемое напряжение; входы могли быть плавающими, калибровки и точности аналогового тракта нет. TPL/MCP физически не проверялись; их операции подтверждают цифровую запись, не движение аналогового выхода. Четыре шаблона ДПКВ — справочные 60-2, 36-1, 24-1, 48-1 (boot default), не шаблоны Voge.

## Офлайн-тесты и сборка

Из `nano_bench/`:

```powershell
python -m unittest discover -s tests -v
python tools\build.py --baud 1000000
```

Для 0.4.0 прошли **30 офлайн-тестов**, включая mock-проверки предохранителей инструментов; два независимых запуска сборки дали один HEX SHA-256: `0b8984c459b2273fde1411001f166c9fd58ac13374781263dee2b46101ac2b93` — он записан в Nano и проверен avrdude 2026-11-15. Историческая публикация 0.3.0: 30 тестов, HEX `a00963641fbded52941ac40a25895a9a1d8d7dab97d0f17303ebe463a7e2df72`.

Проверены Arduino CLI 1.0.4, Arduino AVR core 1.8.6, avr-gcc 7.3 и pyserial 3.5. Если инструменты отсутствуют, установить их нужно явно; скрипт не устанавливает core или зависимости автоматически. Например, ручная установка core: `arduino-cli core install arduino:avr@1.8.6`. Можно указать `--cli`, `ARDUINO_CLI` или поместить CLI в PATH. Каталоги `.build/`, `.cache/`, бэкапы, HEX/ELF и `__pycache__` исключены из Git.

Для сборки/загрузки/резервного копирования применяются подготовленные в модуле скрипты: `python tools/build.py --baud 1000000`; `python tools/upload.py --port COM79 --backup-dir <path> --confirm`; `python tools/backup.py --port COM79 --output-dir <path>`. Загрузка и backup — аппаратные операции, выполнять только при отдельном явном разрешении. Исторические отчёты и сохранённые бэкапы сами по себе не означают, что устройство сейчас подключено или находится в том же состоянии. Переносимые backup/upload прошли mock-тесты и 2026-11-15 реально применены к плате (backup и flash 0.4.0). Перед аппаратной операцией отключить ЭБУ/силовые нагрузки: открытие COM и загрузка сбрасывают Nano, меняют GPIO и (с 0.4.0) автоматически запускают генератор ДПКВ.
